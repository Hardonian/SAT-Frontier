# EPYC campaign resource guard

The 32-worker escalation's preserved `evidence/epyc-independent-validation-20261030T032834Z-2096631/{campaign,resource}.log` records grid_3x10 exact then interruption: 3:28 elapsed, 134,046 major faults, and exit 124. Its 516,380 KiB maximum RSS is not an aggregate process-tree peak. The supplied incident report describes a 29 GiB swap spike; the preserved campaign log does not measure aggregate RAM or establish which allocation caused it. The weighted solver creates an unbounded per-solve memo dictionary of residual-formula keys, with a separate multiprocessing pool worker per cube, making concurrent cache/formula growth a plausible contributor, not a proven attribution. The explicit worker setting bypassed the existing recommendation, whose 50 MiB per-cube estimate is not an enforced cap. The separate four-worker grid_4x7 interruption has no result and an empty resource log; do not conflate it with the 32-worker run.

The campaign harness now refuses real runs outside a Linux cgroup v2 with `memory.max` <= 8 GiB, `memory.swap.max` 0, and `pids.max` <= 32. It caps workers at four and checks host available memory >= 16 GiB plus the cgroup limit before reserving evidence. These are hard aggregate kernel limits, not per-worker RSS estimates; OOM is a failure, never an exact or unknown result. Existing evidence is untouched. Run with a fresh evidence path, e.g. `bash scripts/run_epyc_cut_campaign.sh --instances-dir <dir> --evidence-dir <fresh-dir> --workers 2 --depths 0 1`. The wrapper uses a transient user systemd scope and a 900-second process-group timeout; it requires working cgroup v2 and user systemd. Choose small instances first. An interrupted run retains partial evidence and is not complete. The direct `sat_frontier.epyc_runner` API/CLI and other scripts are not guarded by this campaign check: do not use them for large jobs unless separately placed in a verified bounded scope. Host free memory can fall after the initial check; the fixed cgroup limit is not dynamic host-wide protection.

Verification on this host: unguarded campaign rejected before evidence creation; tiny two-worker campaign produced two exact counts of 3 and passed hash verification; effective limits recorded in its config were 8,589,934,592 bytes, zero swap and 32 tasks. A separate two-child allocation test in a 128 MiB scope triggered kernel OOM and systemd recorded `oom-kill` with 128M peak; the scope was terminated (exit 143), as expected. No large campaign was launched as part of this change.
