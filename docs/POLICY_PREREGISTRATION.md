# Policy train preregistration (v0.2, before campaign)

Hypothesis: deterministic linear branch scores using polarity and short clauses may reduce search nodes or increase solved fraction compared with the existing combined occurrence policy. The component-size term is included to establish its semantics; because components are split before branching, it is constant over branch candidates and cannot affect ranking in the combined solver. The duplicated mixed/component policies are a negative control. Adversarial cases: sparse CNFs, contradictions found by units, and cases where maximizing these signals branches poorly. Model counts must not change; unknown must never be represented as zero.

Freeze the exact five candidates, 4-feature schema, train family/seed parameters and per-worker budgets in `configs/policy-train-v02.json`: 32 independently generated instances, two repeats, existing combined control plus five candidates; total 384 worker runs. No GPU, paid resources, or more than two CPU workers; implementation executes one worker at a time. Node limit is 25, solver wall budget 0.5 s, hard parent deadline 2.5 s including process startup, cache 10,000. Oracle independently checks every exact result (12 variables). Stop and preserve raw records on any mismatch or worker error. Rotating order across repeats/instances mitigates order effects; no warm-up. One Linux worker process per run; record solver time, end-to-end wall time and peak worker RSS if available. No per-worker memory limit is claimed in this slice.

Selection rule, fixed before execution: among candidates only, maximize total exact runs across all train families/repeats; break ties by smallest total search nodes including unknowns, then lexicographically smallest candidate ID. Timing is not used for selection. Archive selected ID, full candidate configuration and SHA-256 hashes of the solver, generator, runner and config before any holdout. Reporting uses per-family per-instance paired differences in solved fraction; cluster bootstrap resamples independently generated instances, never timing repeats, 2,000 replicates and seed 91309. Per-family paired speed ratios only include pairs solved in every repeat, and are explicitly conditional on completion; summarize node/wall limits and all failures separately. Time overhead is ratio of paired mean solver seconds to control on common exact pairs; startup is separately recorded. The confidence intervals are exploratory and not multiplicity corrected, do not establish improvement and cannot substitute for fresh holdout.

Fresh holdout plan, NOT RUN and NOT CONSUMED: use the frozen selected candidate against combined, four target families, n=12 ratio=4, 30 distinct seeds 30001–30030 per family (120 independently generated instances), 5 repeats, same cache/node/wall limits, randomized/rotated run order and independent truth-table oracle, 1200 runs; save formulas and logs in a fresh directory and separately identify the split as consumed on first use. Enforce exact source/config hashes from selection before launching and reject overlapping train instances by content hash. A later implementation must implement those guards; this is a plan, not an executable claim. Holdout analysis must bootstrap across instances and report all outcomes, resource and regressions. This synthetic study alone does not meet the protocol's mature independent solver baseline/performance gate. Any policy change or use of holdout for tuning requires a new disjoint preregistered holdout.
